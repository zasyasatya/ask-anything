Kenapa LLM Saja Tidak Cukup?

❌ Hallucination

LLM mengarang jawaban saat tidak tahu. Tanpa grounding ke dokumen, jawaban terlihat meyakinkan tapi salah.

Q: “Apa SOP cuti di dokumen kami?” A (tanpa RAG): “SOP cuti adalah 12 hari...” // Padahal di dokumen 15 hari + perlu approval HR

⚠️ Outdated & No Private Data

Knowledge LLM cutoff 2024. Dokumen internal perusahaan, PDF SOP, kontrak — tidak pernah dilihat model saat training.

  • Data privat tidak boleh dikirim ke training
  • Perlu jawaban dari file yang baru di-upload 5 menit lalu

✅ Solusi: RAG

Retrieval-Augmented Generation: sebelum menjawab, cari dulu konteks relevan dari knowledge base, lalu suruh LLM menjawab hanya dari konteks itu.

Apa itu RAG? Definisi Lengkap

Retrieval-Augmented Generation = teknik memberikan LLM akses ke external knowledge base saat inference, bukan saat training.

📖 Definisi Formal

Diberikan query q dan corpus dokumen D:

// 1. Retrieval context = retriever(q, D) // top-k chunks paling relevan // 2. Augmentation prompt = f""" Konteks: {context} Pertanyaan: {q} Jawab hanya dari konteks. Sertakan sitasi [1][2]. """ // 3. Generation answer = LLM(prompt)
RAG TRIANGLE

3 komponen harus seimbang — lemah satu, RAG gagal

🎯 Kapan pakai RAG?

  • Data privat / internal (SOP, kontrak, manual)
  • Data yang sering berubah (kebijakan, harga)
  • Butuh sitasi & audit trail
  • Tidak punya budget fine-tuning

STEP 1 — INGESTION PIPELINEDETAIL

Deep Dive: Ingestion — Dari Upload ke Vector DB

Goal: dokumen tersimpan berdasarkan strukturnya, bukan sekadar text blob. Ini kunci untuk retrieval akurat & visualisasi.

📤 1. Upload & Parse (Structure-Aware)

Jangan langsung plain text. Ekstrak struktur:

{ "file": "SOP-Cuti.pdf", "pages": 12, "structure": [ {"type":"heading", "level":1, "text":"SOP Cuti Karyawan", "page":1}, {"type":"heading", "level":2, "text":"1. Jenis Cuti", "page":1}, {"type":"list", "items":["Cuti Tahunan 12 hari","Cuti Sakit..."], "page":2}, {"type":"table", "headers":["Jenis","Durasi","Approval"], "rows":[...]}, {"type":"flow", "text":"Karyawan → Atasan → HR → Selesai"} ] }

⚠️ PDF/DOCX butuh parser khusus: PyMuPDF, pdfplumber, python-docx, markdown-it

✂️ 2. Chunking — Pecah dengan Cerdas

naive: fixed 512 tokenssmart: structure + semantic
// ❌ Naive chunks = split_text(text, 500) // bisa potong tengah kalimat & tabel // ✅ Structure-aware chunks = [] for section in doc.structure: if section.type == "table": keep whole table as 1 chunk if section.type == "heading": merge with next paragraph else: semantic_chunk(section.text, 400, overlap=50)

🧮 3. Embedding

Ubah chunk jadi vektor 768-dimensi. Model: all-MiniLM-L6-v2, bge-m3, OpenAI text-embedding-3-small

emb = embedding_model.encode(chunk.text) # [0.021, -0.34, 0.88, ...] 768 dim
embedding latency ~40ms / chunk

💾 4. Store — Vector DB + Metadata

{ "id": "doc_1_chunk_3", "vector": [0.021, ...], "metadata": { "doc_id": "SOP-Cuti.pdf", "page": 2, "section": "Jenis Cuti", "type": "table", "hierarchy": ["SOP Cuti","Jenis Cuti"], "created_at": "2026-09-17" }, "text": "Cuti Tahunan: 12 hari..." }

DB: Chroma, Qdrant, pgvector, SQLite+sqlite-vss. Metadata hierarchy = kunci untuk visualisasi & filtering.

Chunking Strategy — Visual Comparison

❌ FIXED SIZE (Naive)bad
Bab 1: Jenis Cuti. Cuti tahunan adalah hak karyawan setelah 12 bulan kerja. Cuti ini sebanyak 12 hari kerja. Untuk mengajukan, karyawan harus mengisi form...

Tabel dipotong:
| Jenis | Durasi |
| Cuti Tahun | 12 hari | Cuti Sakit | ... |
  • Potong tengah kalimat → embedding rusak
  • Tabel terbelah → retrieval gagal
  • Hilang konteks hierarki
✅ STRUCTURE + SEMANTICgood
Chunk 1 — Section: Jenis Cuti (p1)
Bab 1: Jenis Cuti. Cuti tahunan adalah hak karyawan setelah 12 bulan kerja sebanyak 12 hari.
metadata: {type: heading+paragraph, hierarchy: [SOP Cuti > Jenis Cuti]}
Chunk 2 — Table: Durasi Cuti (p2, keep whole)
| Jenis | Durasi | Approval |
| Cuti Tahunan | 12 hari | Atasan |
| Cuti Sakit | Sesuai surat dokter | HR |
metadata: {type: table, page:2}
Chunk 3 — Flow: Proses Pengajuan (p3)
Karyawan → Atasan → HR → Selesai
metadata: {type: flow, visualizable: true}
  • Utuh per semantic unit
  • Tabel & flow tidak terpotong → bisa langsung jadi visual
  • Hierarchy tersimpan → bisa filter “hanya dari Bab 1”

🗂️ Kenapa Hierarchy Penting?

  • Filtering: “Cari hanya di Bab 2” → filter metadata.hierarchy contains “Bab 2”
  • Grouping: Saat visualisasi, group chunks per section jadi satu flowchart
  • Citation presisi: Jawaban bisa bilang “Menurut Tabel di halaman 2, Bab 1” bukan cuma “[1]”
  • Visual routing: type=flow → render sebagai flowchart, type=table → render sebagai table interaktif

⚙️ Parameter Penting

  • top-k: berapa chunk diambil (3-10). Terlalu banyak → context bengkak, LLM bingung
  • similarity threshold: mis. 0.75. Di bawah itu jangan dipakai → cegah hallucination
  • reranker: cross-encoder (bge-reranker) untuk urutkan ulang top-k lebih akurat
  • metadata filter: filter dulu per document_id / type sebelum vector search

🛡️ Anti-Hallucination

if max(similarities) < 0.70: return "Maaf, tidak ada info tentang itu di dokumen." else: context = top_chunks answer = LLM(f"Jawab HANYA dari konteks:\n{context}\nJika tidak ada, bilang tidak tahu.")

Apa itu AI Agent? (Bukan Sekadar Chatbot)

🤖 Definisi Agent

Agent = LLM + Tools + Loop + Memory. Dia tidak hanya menjawab, tapi bertindak: memutuskan tool apa yang dipakai, mengeksekusi, mengamati hasil, lalu melanjutkan.

// Chatbot biasa user: "cari SOP cuti" bot: "SOP cuti adalah..." // dari memory, bisa ngarang // Agent user: "cari SOP cuti + buatkan flowchart" agent: 1. think: perlu cari di knowledge base 2. act: call retrieve_knowledge("SOP cuti") 3. observe: dapat 3 chunks + 1 flow structure 4. think: user mau flowchart, ada flow structure 5. act: call create_diagram(flow_data) 6. answer: jawaban + visual flowchart interaktif
AGENT LOOP — REACT
🧠
REASON
🛠️ ACTcall tool
👁️ OBSERVEtool result

🔄 Siklus

  • Reason: LLM mikir “apa yang perlu dilakukan?” (chain-of-thought)
  • Act: pilih tool & argumen (JSON)
  • Observe: baca hasil tool, masukkan ke context
  • Ulang sampai dapat jawaban final atau max_steps habis
for step in range(max_steps): thought = LLM.reason(history) tool_call = LLM.decide_tool(thought) if not tool_call: break result = execute(tool_call) history.append(result)

🧩 Task Decomposition Agent

Agent memecah “Buatkan flowchart SOP cuti” jadi sub-tugas:

Planner (LLM): - User mau flowchart → butuh data flow dari dokumen - Subtask 1: retrieve flow structure - Subtask 2: generate diagram JSON Executor: 1. call retrieve_knowledge(query="proses pengajuan cuti flow", filter={type:"flow"}) → dapat: "Karyawan → Atasan → HR → Selesai" 2. call create_diagram( kind="flowchart", nodes=[{id:"A",label:"Karyawan"},{id:"B",label:"Atasan"}...], edges=[{from:"A",to:"B"}...] ) → dapat: {mermaid:"flowchart TD...", graph:{nodes,edges}} Generator: - Jawab dengan sitasi + render graph JSON sebagai komponen web

💡 Kenapa Agent, bukan RAG biasa?

  • RAG biasa hanya return text. Agent bisa chain tools: retrieve → diagram → chart → table
  • User bisa tanya “Bandingkan SOP lama vs baru” → Agent retrieve 2 dokumen, lalu reasoning
  • Visualisasi butuh tool khusus, bukan hanya text generation

🛠️ Tool Design Principle

  • Single responsibility: 1 tool = 1 tugas jelas
  • Structured I/O: input JSON Schema, output JSON (bukan string)
  • Evidence flag: apakah hasilnya jadi sumber sitasi?
  • Idempotent: panggil 2x hasil sama (kecuali web search)
  • Fast: < 2s ideal, timeout 30s max

Visualisasi: Kenapa Tidak Hanya Mermaid?

❌ Limitasi Mermaid String

  • Hanya string → tidak bisa interaktif (drag, zoom, filter)
  • All-or-nothing: 1 baris salah, seluruh diagram hilang
  • Tidak bisa binding data dinamis (mis. klik node → detail)
  • Styling terbatas, tidak bisa pakai design system app
  • Tidak bisa reuse sebagai data (mis. export ke JSON)
// Mermaid: string ```mermaid flowchart TD A[Karyawan] --> B[Atasan] B --> C[HR] ``` // → render jadi SVG statis, tidak bisa di-drag

✅ Visual sebagai Elemen Web Native

  • Structured JSON → React component → DOM interaktif
  • Bisa pan/zoom/drag node/klik untuk detail relasi
  • Bisa ganti layout (TD/LR), filter, search
  • Bisa export, fullscreen, embed
  • Data tetap ada → bisa jadi sumber untuk tool lain

Best Practices & Pitfalls

✅ Do

  • Simpan struktur: hierarchy, type, page — bukan cuma text
  • Chunk smart: jangan potong table/list/flow, pakai overlap
  • Threshold: jika similarity < 0.7, jangan pakai context (cegah hallucination)
  • Structured JSON first: tool return JSON, bukan string → frontend render
  • Citations: verifikasi di backend, bukan percaya LLM
  • Streaming: SSE untuk delta + tool_call + citations (UX)
  • Timeout & graceful: tool error → jadi data, bukan crash

❌ Don't

  • Jangan chunk fixed 512 tanpa lihat struktur → tabel hancur
  • Jangan langsung embed tanpa cleaning (buang header/footer)
  • Jangan pakai embedding model terlalu besar untuk dev (lambat)
  • Jangan return visual hanya sebagai mermaid string → tidak interaktif
  • Jangan percaya LLM untuk sitasi → harus verifikasi backend
  • Jangan simpan vector di memory saja → harus persistent (Chroma)
  • Jangan lupakan metadata filtering → user mau filter per dokumen

🐛 Pitfalls Umum

  • PDF scanned: text tidak bisa di-extract → butuh OCR (pytesseract)
  • Table kompleks: pdfplumber gagal → fallback ke camelot/tabula
  • Embedding lambat: batch embedding, cache, atau pakai model kecil dulu
  • Context bengkak: top-k terlalu banyak → LLM bingung, batasi 5
  • Hallucination tetap: prompt harus eksplisit “jika tidak ada di konteks, bilang tidak tahu”
  • Visual tidak muncul: pastikan tool return JSON valid + frontend registry ada

❓ FAQ

Q: Embedding model apa yang dipakai?

A: Untuk dev, all-MiniLM-L6-v2 (cepat, 384 dim, 80MB). Untuk prod, bge-m3 (1024 dim, lebih akurat). Bisa juga OpenAI text-embedding-3-small jika ada API key.

Q: Vector DB apa?

A: Chroma untuk kemudahan (persist lokal, no server). Qdrant jika butuh scale. Di repo ini SQLite + sqlite-vss juga bisa untuk zero-ops.

Q: Bagaimana handle PDF scanned (gambar)?

A: Pakai OCR: pytesseract atau easyocr. Cek jika page.get_text() kosong → fallback OCR. Ini stretch goal.

Q: Visual harus pakai library?

A: Tidak wajib. Bar chart bisa pakai div + width %, table pakai HTML table native. GraphView sudah ada di repo, bisa reuse. Yang penting JSON → DOM, bukan string → image.
